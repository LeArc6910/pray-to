# pray-to 설계 문서

초안이다. 정해진 것과 아직 열린 질문을 같이 적는다. 방향이 바뀌면 코드보다 이 문서를 먼저 고친다.

## 어떤 게임인가

코어키퍼 같은 탑뷰 2D 액션·생존·크래프팅 게임이다. 혼자 또는 친구들과 협동으로 지하 세계를 파고들며 보스를 잡고, 그 재료로 다음 단계 장비를 만든다. 전투를 하지 않는 시간에도 농사와 자동화로 꾸준히 성장할 수 있다.

## 핵심 기둥

| 기둥 | 목표 |
|---|---|
| 계단식 성장 | 보스 처치 → 새 재료 → 새 장비 티어 → 새 지역. 단계가 오를 때마다 확실히 체감되도록 수치가 계단 모양으로 오른다 |
| 클래스 조합 | Craft to Exile 2처럼 여러 클래스를 섞는다. 스킬에 태그(화염, 투사체, 소환 등)를 달고 장비·패시브가 태그를 강화해서 조합마다 다른 빌드가 나온다 |
| 보스전 | 페이즈 전환, 예고(텔레그래프)가 있는 패턴, 협동할 때 역할이 갈리는 기믹 |
| 루팅 | 같은 아이템도 접두사·접미사와 룬 소켓으로 매번 다르다. 희귀도가 높을수록 접두사가 많고 강하다 |
| 내실 | 농사와 자동화(채굴·제련·운반). 전투 없이도 시간을 들이면 좋은 보상을 얻는다. 전투와의 시간당 가치를 시뮬레이션으로 비교해 맞춘다 |

## 기술 원칙

### 1. Core가 게임이다

게임 규칙과 시뮬레이션은 전부 `Game.Core`에 순수 C#으로 둔다. 이동·충돌, 전투, 적 AI, 아이템 생성, 인벤토리, 제작, 농사, 자동화가 다 여기 들어간다. Unity는 화면, 입력, 소리, 네트워크 전송만 맡는다.

- 클라우드 세션이 Unity 없이 만들고 테스트할 수 있다
- 호스트 시뮬레이션을 봇으로 돌려 밸런스를 잰다 (`DevTools/CoreSandbox`)
- 충돌은 Unity Physics2D 대신 타일 격자와 원 판정으로 Core에서 직접 한다. 탑뷰 타일 월드라 이걸로 충분하고, 그래야 위 두 가지가 가능하다

### 2. 에디터에서 손으로 만드는 콘텐츠를 두지 않는다

- 월드: 시드 기반 절차 생성
- 아이템·접두사·룬·몬스터·보스·작물·레시피: 데이터 시트에서 에디터 메뉴 한 번으로 에셋을 만든다
- 씬: 시작 씬 하나에 나머지는 코드로 구성

이렇게 해야 대부분의 작업이 클라우드에서 끝나고, 로컬 Unity 작업은 메뉴 실행과 확인으로 줄어든다.

### 3. 멀티플레이는 호스트 권한

- 플레이어 한 명이 호스트(listen server)가 되어 Core 시뮬레이션을 돌린다. 나머지는 입력과 요청을 보내고 결과를 받는다
- 싱글플레이는 "혼자 연 호스트"다. 같은 코드 경로를 쓰므로 멀티 버그가 싱글에서도 드러난다
- 내 캐릭터 이동만 클라이언트가 먼저 움직이고(같은 Core 이동 코드로) 호스트가 받아들인다. 협동 게임이라 치팅 방지보다 반응성을 우선한다
- 적, 피해, 드랍, 인벤토리, 월드 변경(채굴·설치)은 호스트만 결정한다
- 전송은 Netcode for GameObjects와 Unity Transport를 쓴다. Core는 네트워크 라이브러리를 모르고 메시지만 주고받는다
- 실제 메시지와 이동 보정 방식은 `Docs/Multiplayer.md`에 있다

### 4. 결정적 난수와 고정 틱

- Core는 `System.Random` 대신 `GameRandom`(PCG32)을 쓴다. 같은 시드면 .NET 테스트와 Unity(Mono·IL2CPP·Web)가 같은 수를 낸다. 덕분에 월드 시드만 보내면 클라이언트도 같은 지형을 만들 수 있고, 버그와 밸런스 결과를 시드로 재현할 수 있다
- 지형 생성은 정수 연산 위주로 짠다. 부동소수점 연산 결과는 플랫폼마다 미세하게 달라질 수 있다
- 시각(`DateTime.Now` 등)은 Core 안에서 읽지 않고 밖에서 넘겨받는다
- 호스트 시뮬레이션은 초당 30틱으로 돈다. 스냅샷은 2틱마다 보낸다. 농사·자동화도 틱 단위라서 접속하지 않은 동안의 진행을 몰아서 계산하기 쉽다

### 5. 시뮬레이션으로 밸런싱한다

`CoreSandbox`에서 다음을 숫자로 확인한다.

- 드랍 1만 회의 희귀도·접두사 분포
- 봇 파티 대 보스의 승률과 소요 시간
- "전투 1시간"과 "농사·자동화 1시간"의 보상 비교

### 6. 웹 데모는 Unity Web 빌드로 만든다

GitHub Actions(GameCI)로 푸시마다 빌드해 GitHub Pages에 올린다. CI용 Unity 라이선스가 준비되면 붙인다(`LOCAL_TASKS.md` 4번).

## 개발 순서

| 단계 | 내용 | 주로 하는 곳 |
|---|---|---|
| M0 | 저장소 뼈대, Core 테스트 CI, Unity 프로젝트 생성 | 클라우드 + 로컬 |
| M1 | 아이템 = 베이스 + 접두사·접미사 + 룬 소켓, 스탯 계산, 드랍 시뮬레이션 (완료, `Docs/Loot.md`) | 클라우드 |
| M2 | 타일 월드, 이동·충돌, 근접 전투, 적 1종, 2인 협동 접속 (코드 완료, 로컬 플레이 확인 중. `Docs/Combat.md`, `Docs/Multiplayer.md`) | 클라우드 + 로컬 확인 |
| M3 | 보스 1마리 (페이즈, 예고 패턴) (코드 완료, 플레이 확인 전. `Docs/Bosses.md`) | 클라우드 + 플레이 피드백 |
| M3b | 드랍과 인벤토리: 몬스터·보스가 떨어뜨린 M1 아이템을 줍고, 장착하고, 룬을 끼운다. 보스 보상이 다음 단계 장비로 이어진다 | 클라우드 + 로컬 확인 |
| M4 | 클래스 2개와 태그 조합 | 클라우드 |
| M5 | 농사 (작물 1종부터) | 클라우드 |
| M6 | 자동화 (채굴기·운반·제련) | 클라우드 |
| 수시 | Unity Web 빌드 자동화와 배포 | 라이선스 준비 후 |

## 열린 질문

- 최대 협동 인원 (코어키퍼는 8명). 지금은 4명으로 두었다(`HostConfig.MaxPlayers`)
- 인터넷 너머 접속: Unity Relay, Steam 네트워킹 중 무엇을 쓸지
- 클래스 목록과 조합 방식: 주·보조 클래스인지, 자유 조합인지
- 아트 스타일과 해상도: 픽셀아트면 PPU와 카메라 설정이 달라진다
- 월드 크기: 고정인지 무한인지
- 저장: 월드는 호스트 컴퓨터에 두고 캐릭터는 플레이어별로 들고 다니는지
- 회복 수단: 음식(농사와 연결), 물약, 전투 밖 자연 회복 중 무엇을 둘지. 지금은 장비의 생명력 재생 말고는 회복이 없어서 보스전이 작은 피해 누적으로 끝나기 쉽다
