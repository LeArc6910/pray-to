# 웹 데모

`main`의 최신 상태를 브라우저(휴대폰 포함)에서 바로 해 볼 수 있게 하는 빌드와 배포다. 주소는 https://learc6910.github.io/pray-to/ 이다(배포가 켜진 뒤).

## 흐름

1. `main`에 푸시하면 `.github/workflows/web-demo.yml`이 돈다. 문서(`*.md`, `Docs/`)와 `DevTools/`만 바뀐 푸시는 건너뛴다. Actions 탭에서 손으로 돌릴 수도 있다(Run workflow).
2. 시크릿 `UNITY_EMAIL`, `UNITY_PASSWORD`가 없으면 빌드를 건너뛰고 안내만 남긴다(실패로 표시하지 않는다).
3. GameCI의 Unity 이미지(`unityci/editor:ubuntu-<ProjectVersion의 버전>-webgl-3`) 안에서 `.github/scripts/build-web.sh`가 돈다.
   - **라이선스**: 에디터에 들어 있는 Licensing Client로 Unity Personal을 활성화한다(`--activate-ulf --include-personal --username --password`, 시리얼 없음). `--showEntitlements`로 확인하고, 빌드가 어떻게 끝나든 `--return-ulf`로 돌려준다. GameCI의 `unity-builder`는 Personal도 ULF 파일에서 꺼낸 시리얼로 활성화하는데, Unity 6 Personal은 시리얼이 없고 Hub가 ULF를 남기지 않아 "serial invalid"로 실패했다(2026-10-28). 계정은 소셜 로그인이나 2단계 인증 없이 이메일·비밀번호로 로그인할 수 있어야 한다
   - **빌드**: `Game.Client.Editor.WebBuild.RunBatch`. 먼저 `Game > Set Up Project`를 해서 씬과 시트 목록이 최신인지 맞춘 뒤 WebGL로 `build/web`에 빌드한다. `Library/`는 Actions 캐시에 남겨 다음 빌드를 줄인다
4. 결과를 GitHub Pages에 올린다. 처음 빌드는 20분 안팎, `Library` 캐시가 있으면 job 전체가 12분쯤이다(이미지 받기 3분, 빌드 6분).

배포가 끝난 직후 잠깐은 GitHub Pages가 게임 데이터 파일(`web.data.unityweb`)을 요청받아도 503 오류 페이지를 줄 수 있다. 그러면 페이지에 "불러오지 못했습니다: Unknown data format (id=" <!DOCTYPE html>")"가 뜬다. 2026-11-02에 다시 배포한 뒤 바로 열었을 때 한 번 나왔고, 브라우저 캐시에 그 응답이 503으로 남아 있었다. 새로고침하자 바로 떴다. 배포 직후가 아닌데도 되풀이되면 클라우드에 알린다.

에디터가 시작 1초 만에 `Killed`(종료 코드 137)로 끝나는 일이 있다(2026-10-28 첫 열두 번 중 세 번. 다시 띄우면 늘 됐다). 원인은 아직 모른다. 그래서 `build-web.sh`가 137로 끝났을 때만 같은 라이선스로 에디터를 세 번까지 다시 띄운다. 세 번 모두 그러면 Actions 탭에서 Re-run failed jobs를 누르고 클라우드에 알린다.

빌드 설정(`ProjectSetup.UseWebSettings`): gzip 압축에 decompression fallback을 켠다. GitHub Pages는 `.gz` 파일에 `Content-Encoding` 헤더를 붙이지 않으므로, 브라우저 대신 Unity 로더가 압축을 푼다. 데이터 캐싱도 켜서 두 번째 접속부터는 빨리 뜬다.

로컬에서 빌드만 해 보려면 에디터 메뉴 **Game > Build Web Demo**(결과는 `Builds/Web`, 커밋하지 않는다). 아무 정적 서버로 그 폴더를 띄우면 된다. 예: `python -m http.server 8000 --directory Builds/Web` 후 같은 Wi-Fi의 휴대폰에서 `http://<PC 주소>:8000`. 빌드하면 Unity가 URP 에셋 몇 개(`URP-2D.asset`의 셰이더 프리필터 설정, `UniversalRenderPipelineGlobalSettings.asset`, `DefaultVolumeProfile.asset`)를 고쳐 쓰는데, 게임에는 영향이 없으니 되돌려도 된다. Burst가 저장소 루트에 만드는 `Data/`는 무시된다.

사람이 고른 다음 작업 후보 5번. 첫 접속에 받는 양과 메뉴가 뜨기까지의 시간을 쟀다(헤드리스 Chromium, 캐시 없이 두 번).

- **고치기 전**(`b2c6eed`): 20.9 MB를 받는다(wasm 13.4 MB, 데이터 6.9 MB, 모두 gzip). 엔진이 뜨는 데 2.3~3.9초, 메뉴가 보이는 데 5.2~6.6초다. 그 사이 2.5~3초는 유니티 시작 화면이었다
- **데이터가 큰 까닭**(웹 빌드 로그의 Build Report):
  - 유니티 로고 시작 화면: 2.7 MB
  - URP 필름 그레인 텍스처 열 장: 2.5 MB(후처리를 쓰지 않는데도 Unity 6 URP가 넣는다)
  - 글꼴: Noto Sans KR 0.5 MB, Galmuri 0.3 MB
  - 셰이더: 0.5 MB
- **고친 것**(`ProjectSetup.UseWebSettings`, 웹 빌드가 부를 때마다 다시 맞춘다):
  - 시작 화면을 끈다(Unity 6은 Personal도 끌 수 있다)
  - URP 전역 설정의 "쓰지 않는 후처리 변형과 자원 빼기"를 켠다. 이름으로 찾아 켜므로 URP 버전이 이름을 바꾸면 아무 일도 하지 않는다
  - IL2CPP 코드를 속도 대신 크기에 맞춰 만든다
- **하지 않은 것**: 코드 줄이기(managed stripping) 단계를 올리면 wasm이 더 줄지만, Relay·인증이 쓰는 Newtonsoft JSON의 리플렉션이 깨질 수 있어 두었다. Brotli는 GitHub Pages가 압축 헤더를 붙이지 않아 로더가 자바스크립트로 풀어야 해서, 휴대폰에서는 오히려 느릴 수 있다
- **고친 뒤**(`c326355`, 같은 방법): 17.0 MB(wasm 11.8 MB, 데이터 4.6 MB)로 19% 줄었다. 엔진이 뜨는 데 1.8~2.0초, 메뉴가 보이는 데 2.9~3.1초로 절반쯤이다. 휴대폰 회선에서는 받는 양이 시간을 더 좌우하므로 차이가 더 클 수 있다

`Docs/Research2026-11.md`의 웹 데모 점검 항목을 다시 확인했다(배포 `ef276c9` 이후 페이지, 헤드리스 Chromium, 캐시 없이 PC·휴대폰 크기 각 두 번).

- 첫 탭 전에는 소리가 나지 않는다: 브라우저가 사용자 입력 전 소리를 막고, Unity가 첫 입력에서 소리를 연다. 메뉴의 첫 탭이 그 입력이다
- 남은 것: 실제 iPhone Safari에서 메모리가 넘쳐 페이지가 다시 불리는지(사람 확인, `LOCAL_TASKS.md` 111단계). 코드 줄이기 단계 올리기는 위의 까닭으로 여전히 두었다

## 웹에서 달라지는 것

- **협동은 온라인 방으로.** 브라우저는 연결을 받을 수 없어 LAN 호스트는 숨기고, Unity Relay를 거치는 [온라인 방 만들기]와 [코드로 참가]만 둔다. PC 버전과도 한 방에서 논다(`Docs/Multiplayer.md`의 "온라인", 2026-11-02). 프로젝트를 Unity Cloud에 연결하고 Relay를 켜기 전에는 오류 문장만 나온다
- **글꼴**: 웹 빌드는 시스템 글꼴을 쓸 수 없어서 Noto Sans KR(SIL OFL 1.1, `Docs/Licenses/NotoSansKR-OFL.txt`)을 게임에 넣었다. 10 MB짜리 원본에서 Medium 굵기와 필요한 글자(ASCII, 기호, KS X 1001 한글 2,350자, 코드와 시트에 쓰인 모든 글자)만 남겨 약 520 KB다. 새 글자가 필요하면 `DevTools/Fonts/make-korean-font.py`로 다시 만든다. 에디터와 PC 빌드도 같은 글꼴을 쓴다
- **도트 글꼴**(2026-11-02): 기본 글꼴은 도트 글꼴 Galmuri11 Bold(quiple, SIL OFL 1.1, `Docs/Licenses/Galmuri-OFL.txt`)다. 메뉴의 "글꼴: 도트/매끈"으로 위의 Noto Sans KR로 바꿀 수 있고 기기에 남는다(`Settings.PixelFont`). Galmuri 가운데 Bold를 고른 것은 모든 글리프가 지은이의 창작이어서다(보통 굵기의 한글 2,355자는 닌텐도 DS 글꼴에서 왔다). 같은 글자 범위로 줄여 약 300 KB이고 `DevTools/Fonts/make-pixel-font.py`로 다시 만든다. 도트가 네모로 남도록 12px(설계 크기)이나 그 정수배로만 그린다: 코드의 글자 크기는 `Ui.Text`가 12의 배수로 맞추고(13·15→12, 20→24, 34→36), 굵게는 이미 굵은 글꼴이라 끈다. 글자가 줄 가운데 오도록 줄의 세로 치수를 고쳤다: 원래는 16px 줄에서 글자 위가 1px, 아래가 4px(줄 간격 2px 포함)라 막대·단추 안 글자가 위 테두리에 닿았다(2026-11-02 점검). 같은 16px 줄을 기준선 위 13px, 아래 3px로 나눠 글자 위 2px, 아래 3px다(`make-pixel-font.py`의 `center_vertically`). 생명력 막대도 22점으로 높였다. 가져오기 설정(12px, Hinted Raster, 없는 글자는 Noto로)은 `ProjectSetup`이 하고, 글꼴 텍스처는 가장 가까운 픽셀로 읽어 화면 배율로 커져도 흐려지지 않는다. 도트 글꼴이 아직 프로젝트에 없으면 Noto로 그린다
- **페이지**: 프로젝트의 템플릿 `Assets/WebGLTemplates/Fit`(Unity의 Minimal 템플릿을 고친 것, `ProjectSetup.UseWebSettings`가 고른다). 게임이 PC에서도 브라우저 창을 꽉 채워서, 작은 창에서 960×600 고정 화면이 잘리고 스크롤 막대가 생기던 일이 없다(2026-10-31 UI 점검). 불러오는 동안 "불러오는 중…" 막대를 보여 준다. Tab은 가방을 여는 키라서 브라우저가 Tab으로 초점을 게임 밖으로 옮기지 않게 막는다. 저장본과 설정 파일이 바뀌면 Unity가 브라우저 저장소로 옮기게 한다(`autoSyncPersistentDataPath`, `Docs/Saving.md`). 게임이 뜨면 브라우저에 사이트 저장소를 지우지 말라고 한 번 청한다(`navigator.storage.persist()`, 2026-11-09). 휴대폰 브라우저는 오래 안 연 사이트의 저장소를 비우기도 하는데 그 일을 줄인다. 브라우저가 거절할 수도 있다
- **키 입력과 초점**(2026-11-02): 브라우저는 초점을 가진 페이지에만 키를 보낸다. 그런데 Unity는 브라우저 창이 시스템의 활성 창이 아니면 페이지에 초점이 없다고 보고, Input System이 클릭으로 초점이 돌아올 때까지 키를 버렸다(시작 직후 Tab이 듣지 않던 일). 웹 빌드에서는 들어온 키를 그대로 쓰고(`InputSettings.BackgroundBehavior.IgnoreFocus`), 페이지가 초점을 잃으면 눌린 키를 놓는다(`Controls.HearKeysWithoutFocus`)
- **화면 크기**: 브라우저는 기기의 실제 픽셀 밀도로 그리므로(휴대폰은 점 하나에 3픽셀쯤) 그대로면 글자가 아주 작다. `Ui`가 `window.devicePixelRatio`(`Plugins/WebGL/Display.jslib`)만큼 IMGUI를 키운다. 세로 화면에서는 카메라를 넓혀 가로로 보이는 범위를 지킨다. 가로로 들고 하는 쪽이 편하다

## 터치 조작

| 동작 | 하는 법 |
|---|---|
| 이동 | 화면 왼쪽 절반을 누르고 끈다. 누른 곳에 스틱이 생기고, 덜 끌면 천천히 걷는다 |
| 공격 | 화면 오른쪽 절반을 누른다. 누른 곳에 붉은 스틱이 생기고, 누르고 있는 동안 계속 공격한다(검은 휘두르고 활·지팡이는 쏜다). 스틱을 끄는 방향으로 공격하고, 거의 끌지 않으면 걷는 방향(서 있으면 바라보던 방향)으로 공격한다 |
| 스킬 | 오른쪽 아래 구석의 버튼 4개(2×2). 공격 스틱을 잡고 있으면 그 쪽으로, 아니면 8칸 안의 가장 가까운 적 쪽으로(없으면 바라보는 쪽으로) 쓴다(2026-11-11, 엄지 하나로 쓰게). 다른 손가락으로 스틱을 잡은 채 눌러도 된다. 메뉴에서 고른 클래스의 스킬이 들어간다(`Docs/Classes.md`) |
| 지도 | 오른쪽 위 미니맵을 탭하면 전체 지도가 크게 열린다. 아무 데나 다시 탭하면 닫힌다. 가 본 곳만 보인다 |
| 가방 | 미니맵 아래 [가방] 버튼. [장비], [재료·제작], [스킬], [특성] 탭이 있다. [장비]는 칸 격자라 칸을 누르면 아래에 설명과 단추가 나온다. 재료 이름을 누르고 있으면 설명이 보인다. 재료의 [놓기]·[심기], 제작 목록의 [만들기]는 [재료·제작] 탭에 있다 |
| 캐기 | 곡괭이를 들고(퀵슬롯) 벽 쪽으로 공격 스틱을 끌고 누르고 있는다(`Docs/Crafting.md`) |
| 퀵슬롯 | 스킬 버튼 옆 아래 줄의 6칸(자리가 없으면 스킬 버튼 위). 탭하면 쓴다. 아래 "퀵슬롯" |
| 나가기 | 미니맵 아래 [나가기] 버튼 |

버튼, 미니맵, 가방 창 위에서 시작한 터치와 지도가 크게 열려 있는 동안의 터치는 조작으로 치지 않는다. 터치를 한 번이라도 하면 버튼과 안내가 터치용으로 바뀐다. 휴대폰·태블릿 브라우저(`Application.isMobilePlatform`)에서는 처음부터 터치용이다(2026-11-09, 첫 목표 "클래스 고르기"가 [가방] 단추를 가리키는데 첫 터치 전에는 PC 화면이라 그 단추가 없었다). 브라우저는 탭을 마우스 클릭으로도 보내므로 마지막 터치 뒤 1초 동안은 마우스를 무시한다.

### 터치 단순화 (2026-11-11)

조사 보고서 후보 16. 테라리아 모바일이 받은 비판(동시 입력이 많다, 작은 단추)을 피하려고:

- **엄지 하나로 스킬**: 스킬 단추만 누르면 8칸 안(`GameRoot.AutoAimReach`)의 가장 가까운 몬스터·보스 쪽으로 쓴다. 공격 스틱을 당긴 채 누르면 전처럼 그 쪽이다
- **스틱을 톡 치면 가까운 적에게**: 공격 스틱을 당기지 않고 누르기만 하면 걷는 쪽 대신 가장 가까운 적 쪽으로 휘두른다. 벽을 캘 때는 전처럼 벽 쪽으로 당긴다
- **상황별 단추는 이미 있다**: 말 걸기, 잠자기, 기계 끄기, 기지 방어, 균열, 집에서 일어나기는 그 물건이나 사람 위에 뜨는 단추라, 가까이 가면 그것만 보인다
- **저장 내보내기 안내**: 웹과 휴대폰에서 저장본이 있는데 한 번도(또는 7일 넘게) 내보내지 않았으면 메뉴의 [저장본] 단추 아래에 노란 글씨로 "저장본은 이 브라우저(앱)에만 있습니다…"가 뜬다(`SaveMenu.ExportDue`). [전부 내보내기]나 하나 [내보내기]를 하면 7일 동안 사라진다

## 퀵슬롯

사람 요청(2026-11-01): "화면 하단 부분에 퀵슬롯을 만들어서 아이템을 올려놓고 장비가 있으면 교체하고 물약 같은 아이템이 있으면 사용하게". `Scripts/Client/Hotbar.cs`.

- **자리**: 화면 아래 6칸. PC는 스킬 칸(Q E R F C) 바로 위 가운데, 휴대폰은 스킬 버튼 옆 아래 줄(세로 화면처럼 자리가 없으면 스킬 버튼 위). 가방이 열려 있으면 숨는다
- **쓰기**: PC는 1~6 키(메뉴의 [키 바꾸기]에서 바꿀 수 있다)나 클릭, 휴대폰은 탭. 칸을 누르는 손가락이나 클릭은 이동·공격으로 치지 않는다
- **올리기·내리기**: 가방의 아이템·물약·재료 줄 끝의 [퀵]을 누르면 첫 빈 칸에 올라가고 단추가 [퀵2]처럼 칸 번호가 된다. 다시 누르면 내린다. 6칸이 다 찼으면 가방 위에 알려 준다
- **하는 일**: 장비는 그 칸에 낀다. 무기면 손에 들고, 들던 것은 가방으로 간다(검 ↔ 곡괭이). 지금 끼고 있는 장비 칸은 금색 테두리다. 물약은 마시고 음식은 먹는다(대기 시간 동안 어둡다). 놓는 재료(횃불·작업대·기계·돌)는 앞에 놓고, 씨앗은 앞에 심고, 물뿌리개는 앞 3×3칸에 물을 준다. 다 쓴 칸은 흐려지고, 다시 생기면 그대로 쓴다
- **기억**: 캐릭터 이름마다 이 기기에 남는다. 아이템은 번호가 아니라 이름·등급·능력치로 기억해서 다음 접속에도 같은 아이템을 찾고, 그 아이템이 없어지면 같은 종류(예: 다른 구리 곡괭이)를 쓴다. 호스트는 퀵슬롯을 모르고, 가방의 단추를 누른 것과 같은 명령만 받는다
- **처음 칸**: 퀵슬롯을 처음 쓰는 캐릭터는 들고 있는 무기, 곡괭이, 첫 물약, 횃불이 1~4칸에 들어가 있다

## 설정

메뉴의 설정은 모두 기기에 기억된다(`Settings.cs`, 설정 파일 `settings.txt`, `Docs/Saving.md`).

- [어둠과 빛], [효과음: 100%](끔·25·50·75·100%), [음악: 50%](같은 단계, 메뉴에서도 동굴 곡이 나온다), [개발 정보]
- [목표 안내](2026-11-03): 끄면 목표 목록의 목표와 "목표 달성" 알림, 소리가 나오지 않는다. 목표는 그대로 세고 보상도 받는다. 다시 켜면 그 캐릭터가 와 있는 목표부터 보인다(`Docs/Guide.md`)
- [화면 흔들림](2026-11-03): 끄면 맞거나 근처에 큰 공격이 떨어져도 화면이 흔들리지 않는다. 번쩍임과 소리는 그대로다
- [저장본: 고르기·내보내기·가져오기]: 오른쪽 칸이 이 기기의 캐릭터·월드 목록이 된다. 웹에서는 파일을 내려받고, 가져올 때는 게임 위에 뜨는 상자에서 파일을 고른다(`Docs/Saving.md`의 내보내기와 가져오기)
- [키 바꾸기](키보드가 있을 때만 보인다): 오른쪽 칸이 클래스 대신 키 목록이 된다. 스킬 1~4, 물약, 가방, 지도, 퀵슬롯 1~6, 기계 켜기/끄기의 단추를 누르고 쓸 키를 누른다. 다른 일에 쓰던 키면 둘이 서로 바뀐다. Esc는 그만두기, [처음 키로]는 모두 되돌리기. 가방은 정한 키 말고 I로도 열린다(I를 다른 일에 쓰지 않을 때)

## 개발 정보

메뉴의 [개발 정보: 꺼짐]을 누르면 화면 왼쪽 아래에 숫자 창이 뜬다(`DevInfo.cs`, 기기에 기억된다). 휴대폰 성능과 입력 문제를 숫자로 보려고 만들었다.

- 첫 줄: 초당 프레임, 한 프레임에 걸린 시간, 그중 어둠 계산에 걸린 시간(밀리초, 1초쯤으로 고른 값)
- 둘째 줄: 화면 크기(픽셀), 게임이 쓰는 크기(점), 점 하나의 픽셀 수(브라우저의 `devicePixelRatio`)
- 그 아래 최근 입력 10줄: 앞의 숫자는 프레임 번호와 시각이다
  - "입력 시스템 ↓Tab"은 게임이 실제로 읽는 쪽(Input System)이 본 누름이다
  - "IMGUI ↓Tab"은 화면 UI 쪽이 받은 같은 키다
  - "→ 가방 열림"은 게임이 한 일이다
  - 누른 키가 IMGUI 줄에만 있고 입력 시스템 줄에 없으면, 브라우저는 키를 넘겼는데 게임이 놓친 것이다. 둘 다 없으면 브라우저나 자동 입력 도구가 키를 넘기지 않은 것이다

- 글자 크기와 HUD·가방 창 배치가 화면에 맞는지
- 프레임이 충분히 나오는지
